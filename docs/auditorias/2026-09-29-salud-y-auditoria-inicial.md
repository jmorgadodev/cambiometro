## Estado operativo

`/api/v1/health` responde HTTP 200 con `ok=true` y `r2=true`. El backend público es R2 y `publicD1Reads=false`. El campo `d1=true` sólo indica que existe un binding D1; no certifica la consistencia de sus filas.

La respuesta actual de producción incluye `d1Consistent=false`, `d1TransferRows=0` y `d1ReleaseChecksum=null`. El chequeo opcional de D1 está desactivado por diseño para evitar lecturas rutinarias. En el código desplegado, un chequeo no solicitado se serializa como `false/0`; por ello **no hay evidencia de una divergencia real D1↔R2**, sino un estado “no comprobado” presentado como si fuera “inconsistente”.

La sonda de cuota ejecutada el 29-sep-2026 informa `D1 level=ok`; luego probó una consulta paginada a `/api/v1/records?source=camara&limit=1`, que respondió desde el backend R2 con estado parcial. Esa sonda acredita nivel de uso y disponibilidad de una página R2, no coteja el puntero de transferencias D1 con su manifest.

En esta rama se ajustó el contrato de salud: añade `d1CheckStatus` (`not-requested`, `consistent`, `inconsistent`, `unavailable`) y devuelve `null` para consistencia/conteo cuando no se ejecutó el chequeo. Esto no activa D1, no cambia el backend público y no se ha desplegado.
